# MedCue 决赛产品主线计划

状态：已由产品负责人确认；产品实现尚未进入 M1<br>
建立日期：2026-08-22<br>
最近校准：2026-08-23

## 1. 一句话定位

MedCue 是面向一般用药人群的本地优先用药管理工具。它帮助用户看清当前任务、完成或更正动作，并留下可信记录；适老模式是旗舰差异化体验，但不是唯一用户范围。

## 2. 核心价值

普通提醒只解决“到点响一下”。MedCue 重点解决提醒之后的问题：

- 用户能否一眼认出当次药品和应做动作；
- 没有操作时是否诚实保留为“未确认”，而不是猜成漏服或主动跳过；
- 延后、补记、更正、重开和重启后，记录是否仍一致；
- App、通知、Live Activity 与 Watch 是否指向同一份已提交事实；
- 普通模式和适老模式是否共用同一套药品、计划、任务和动作日志；
- 记录能否转成复诊时可核对、无诊断结论的摘要。

核心竞争力按优先级是：低认知负担、诚实动作语义、可靠可更正闭环、双模式同源、本地优先隐私。AI、趋势、视觉特效和功能数量只能辅助这些价值。

## 3. 用户与范围

通用底座服务长期、多药、多时段或短期复杂疗程用户，以及需要回顾和复诊沟通的人。适老模式重点服务不熟悉复杂界面、多步骤和长说明文字的长辈。

当前范围：

- 家属在同一台 iPhone 上协助录入、核对设置；
- 适老首页一次突出一个当前任务；
- 主要动作只有“已服用”“稍后提醒”“需要帮助”；
- 无操作保持“未确认”；
- 普通模式保留主动跳过、原因、更正、重开和详细核对；
- 两种模式共享数据与应用命令。

当前不做：

- 远程子女端、异常推送和远程改计划；
- 医生小程序、医生账号或临床记录系统；
- 多人账号、云端照护团队权限；
- 以 AI 代替医生、药师或自主改变用药。

“需要帮助”的最小方向是调用 iOS 系统确认界面联系用户预先设置的号码，不上传通讯录。具体可见行为要在 M1 原型验收后固定。

## 4. 双模式边界

适老模式与普通模式是同一已提交状态的两种呈现，不是两个 App 或两套数据库。相同逻辑动作必须调用相同应用命令，遵守相同事务、幂等、回滚和隐私规则。

适老模式不在主操作面放主动跳过和原因填写，复杂核对与纠错可切回普通模式完成。切换模式不得复制计划、任务、日志、提醒或副作用。

## 5. 决赛里程碑

前一阶段未达标，不用新增功能掩盖问题。

| 阶段 | 目标 | 退出证据 |
| --- | --- | --- |
| M0 基线 | 固化方向、边界、工具和协作顺序 | 权威文档一致；Xcode 27 本机工具链已验收；无旧路径或旧插件作为当前指引 |
| M1 最小原型 | 定义适老模式问题、旅程和界面 | 同机协助设置、单一任务卡、三个动作、未确认语义、VoiceOver、动态字体和大触控区域均有明确验收脚本 |
| M2 最小闭环 | 在同一数据底座完成服用、延后、求助和未确认 | 共享命令与数据；保存成功后才反馈；重启状态正确 |
| M3 可靠闭环 | 补齐更正、重开、幂等、重复点击、失败与恢复 | Swift Core、iOS hosted、关键 XCUITest 和真机分层证据；失败不显示虚假成功 |
| M4 双模式与摘要 | 普通模式可核对纠错，摘要支持沟通 | 模式切换历史一致；摘要只陈述有证据的记录，不做诊断 |
| M5 真机与用户验证 | 证明真实设备和真实理解条件下可用 | VoiceOver、动态字体、真机脚本和代表性非开发参与者任务记录；限制如实记录 |
| M6 决赛整合 | 形成稳定演示和可复现交付 | 演示不依赖临时网络；源码包、CI、真机备份路线和所有声明均可追溯 |

真机端侧模型 Issue #28 只有在 M2/M3 的本地闭环证据完成后才进入评估，不抢占适老闭环。

## 6. 准入规则

工作同时满足以下条件才进入当前主线：

1. 直接减少真实用药的理解成本、错误风险或记录不可信；
2. 能用清楚场景展示价值；
3. 有可观察验收标准和对应证据层；
4. 不提前引入远程身份、云同步或医生系统；
5. 收益明显高于实现、测试与维护成本。

## 7. 本机与 YZY 顺序

本机主线负责产品方向、Xcode、SwiftData、适老模式、真机、本地模型和决赛演示。YZY 只负责已明确授权且与本机文件不重叠的 Windows 可执行工作。

截至 2026-08-23 的串行顺序：

1. Issue #39 / PR #40 已合入为 `main@c474169`，准确 PR HEAD 与合入后 `main` 的完整 Native Verification 均成功；
2. Issue #5 是 YZY 的下一项可复现决赛源码包工作，目前仍为已指派、无分支的排队状态；启动前须记录最新 `main` 和开放文件重叠核对；
3. 本机继续自己的产品里程碑，不替 YZY 重做或擅自启动其远端任务。

## 8. GitHub 使用边界

本机一次推进一个可验收小步，并可在一个聚焦里程碑分支内连续验证。GitHub 用于远程协作、长期 backlog、Pull Request、准确提交 CI 和进入 `main` 的整合门，不作为每个本地动作的前置条件。

任何开放 Pull Request 已修改目标文件时，遵守一文件一写入者，等待串行整合或明确记录文件边界。隐私、用药记录、医疗 AI、迁移、授权、可信 CI 和发布脚本仍需与风险相称的独立复审。

## 9. 调整原则

只有真实用户理解问题、真机证据、比赛规则、官方日期或已验证工程阻塞可以改变顺序。调整时说明它如何增强核心价值或降低交付风险，不用功能数量保护旧想法。
